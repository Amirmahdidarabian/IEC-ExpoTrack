# ابزار انتشار IEC ExpoTrack برای Ubuntu

بعد از نصب یک‌باره، منوی نسخه‌ها را باز کنید:

```bash
sudo iec-deploy
```

این محیط داخل SSH است، نه پنل عمومی وب. این ابزار برای **همین سرور و مخزن** ساخته شده است، نه یک سرویس عمومی اجرای کد. فقط مدیر دارای دسترسی root/sudo باید از آن استفاده کند و فقط برنچ‌های بررسی‌شده و مورداعتماد را منتشر کند. مخزن از قبل باید در `/opt/IEC-ExpoTrack` و برنامه و دیتابیس فعلی سالم و روشن باشند.

## انتخاب نسخه در منو — نسخهٔ ابزار 1.1.0

با `iec-deploy` یا `iec-deploy menu`، ابتدا برنچ‌های موجود GitHub، SHA، تاریخ آخرین commit، نویسنده و عنوان آخرین تغییر نمایش داده می‌شوند. دریافت این فهرست فقط cache اختصاصی Git ابزار را تازه می‌کند؛ checkout، اپ، دیتابیس و برنچ‌های محلی تغییر نمی‌کنند. از روی ایمیج واقعی app، نسخهٔ در حال اجرا با `[RUNNING]` مشخص می‌شود. اگر ایمیج قدیمی برچسب SHA نداشته باشد، نسخهٔ فعال `unknown` نشان داده می‌شود؛ HEAD مخزن به‌اشتباه نسخهٔ فعال نامیده نمی‌شود.

1. شمارهٔ نسخه یا نام برنچ را وارد کنید.
2. SHA کامل، پنج commit آخر و تعداد فایل‌های migration آن نسخه را ببینید.
3. برای انتشار، دقیقاً عبارت خواسته‌شده، مثلاً `deploy v0.8`، را تایپ کنید. ورود هر چیز دیگر انتخاب را لغو می‌کند.
4. `r` فهرست را تازه می‌کند و `q` بدون انتشار خارج می‌شود. انتخاب نسخه‌ای که همان commit آن در حال اجراست، انتشار تکراری شروع نمی‌کند.

برای نمایش فهرست بدون هیچ سؤال یا انتشار:

```bash
iec-deploy branches
```

`iec-deploy v0.8` هم ابتدا فهرست و جزئیات نسخهٔ انتخاب‌شده را نشان می‌دهد و تأیید می‌خواهد؛ دیگر فوراً انتشار را شروع نمی‌کند. اگر برنچ بین پیش‌نمایش و اجرای job تغییر کند، قبل از بک‌آپ، checkout و migration متوقف می‌شود و باید نسخهٔ جدید را دوباره بررسی کنید. هنگام deployment فعال، دریافت فهرست و نصب نسخهٔ جدید ابزار به کمک همان قفل متوقف می‌شود؛ `status` و `logs` همچنان در دسترس‌اند.

**انتخاب نسخهٔ قدیمی به معنای restore دیتابیس قدیمی نیست.** برنامه فقط وقتی اجازهٔ انتشار می‌دهد که migrationهای اعمال‌شده در نسخهٔ انتخابی موجود و بدون تغییر باشند و سایر کنترل‌های قبلی پاس شوند. این کنترل تضمین کامل سازگاری رفتاری نسخهٔ قدیمی با داده‌های جدید نیست. اگر نسخهٔ قدیمی migration جدیدتر را ندارد، ابزار عمداً مانع انتشار می‌شود؛ برای دورزدن آن migration را پاک نکنید. rollback همراه با تغییر دیتابیس نیاز به بررسی جداگانه دارد.

## نصب یک‌باره

پیش‌نیاز: Ubuntu با systemd، Python 3.10 یا جدیدتر، Git و Docker Compose V2. ابزار به npm، Node یا پکیج Python روی میزبان نیاز ندارد و چیزی را خودکار با apt نصب نمی‌کند.

فایل بستهٔ `iec-deployer.tar.gz` را از کامپیوتر به سرور منتقل کنید. مثال **CMD ویندوز** برای بسته‌ای که در پوشهٔ outputs همین پروژه ساخته شده است:

```cmd
scp -P 9011 "C:\Users\User\Desktop\IEC ExpoTrackC\outputs\iec-deployer.tar.gz" root@141.11.45.44:/root/iec-deployer.tar.gz
ssh -p 9011 root@141.11.45.44
```

داخل **SSH سرور**، نه CMD ویندوز:

```bash
mkdir -p /root/iec-deployer
tar -xzf /root/iec-deployer.tar.gz -C /root/iec-deployer
bash /root/iec-deployer/install-deployer.sh
iec-deploy --version
```

نصب فقط فایل اجرایی و راهنما را کپی می‌کند؛ سایت را منتشر نمی‌کند. برای به‌روزرسانی خود ابزار، ابتدا مطمئن شوید هیچ deployment در حال اجرا نیست، بستهٔ بررسی‌شدهٔ جدید را منتقل کنید و دوباره installer را اجرا کنید. ابزار با دریافت برنچ خودش را خودکار جایگزین نمی‌کند.

## استفادهٔ روزمره

```bash
iec-deploy v0.8
```

نام می‌تواند مثل `release/v0.8` هم باشد. بعد از پیش‌نمایش و تأیید، ابزار SHA همان برنچ را هنگام دریافت با SHA تأییدشده تطبیق می‌دهد و همان commit را می‌سازد؛ هیچ force push، reset یا پاک‌کردن تغییرات محلی انجام نمی‌دهد. برنچ باید قبلاً روی GitHub منتشر شده باشد. احراز هویت Git سرور باید از قبل کار کند؛ ورود تعاملی یا نمایش token هنگام deployment انجام نمی‌شود.

کار در یک سرویس موقت systemd اجرا می‌شود؛ قطع SSH یا بستن پنجره کار را متوقف نمی‌کند. `Ctrl+C` فقط نمایش لاگ را می‌بندد، نه سرویس deployment را. قفل بین پردازش‌ها اجازه نمی‌دهد دو deployment هم‌زمان مخزن را تغییر دهند.

```bash
iec-deploy status
iec-deploy logs
```

برای دیدن یک اجرای قبلی، شناسهٔ چاپ‌شده را اضافه کنید:

```bash
iec-deploy status JOB_ID
iec-deploy logs JOB_ID
```

## کارهایی که خودکار انجام می‌شوند

1. کنترل مسیر مخزن، origin مجاز، تمیزبودن Git و وجود `.env`؛ تغییر محلی باعث توقف می‌شود، نه حذف یا stash خودکار.
2. دریافت برنچ، ثبت SHA هدف و بررسی نبودن فایل‌های حساس/تولیدی در Git.
3. بررسی Compose: دیتابیس، شبکه‌ها و volumeها نباید تغییر کنند؛ پورت دیتابیس عمومی نیست و اپ فقط `127.0.0.1:3000` منتشر می‌شود. تغییر زیرساخت به بررسی دستی نیاز دارد.
4. بررسی migrationهای قبلی و فضای آزاد؛ تغییر checksum یا حذف migration اعمال‌شده باعث توقف می‌شود.
5. ذخیرهٔ ایمیج واقعی قبلی و ساخت بک‌آپ جدید PostgreSQL قبل از هر migration؛ فایل خالی یا شکست `pg_restore --list` مانع ادامه می‌شود. checksum بک‌آپ ذخیره می‌شود. خواندن فهرست آرشیو جای آزمایش restore کامل در دیتابیس غیرproduction را نمی‌گیرد.
6. ساخت ایمیج جدید از یک آرشیو جداگانهٔ فایل‌های tracked همان SHA در حالی که اپ قبلی روشن است؛ فایل‌های untracked، `.env` واقعی، بک‌آپ و فایل‌های خصوصی میزبان وارد build context نمی‌شوند. SHA در برچسب OCI ایمیج ثبت می‌شود.
7. اجرای `prisma migrate deploy` با ایمیج و نسخهٔ Prisma خود پروژه. **Migrationهای جدید ممکن است ساختار یا داده را تغییر دهند؛ SQL آن‌ها باید قبل از انتشار بازبینی شده باشد.** ابزار ایمن‌بودن معنایی SQL دلخواه را تضمین نمی‌کند.
8. جایگزینی فقط سرویس app؛ دیتابیس موجود recreate یا restart نمی‌شود.
9. انتظار برای healthcheck، تطبیق ایمیج در حال اجرا، دریافت کامل صفحه و فایل‌های اصلی JS/CSS از origin، و کنترل HTTPS دامنهٔ اصلی.

دامنهٔ کنترل‌شده فقط `iecexpotracker.com` است؛ مطابق انتخاب مالک، `www` اجباری نیست.

## شکست و بازگشت

- شکست قبل از تعویض app: اپ قبلی عمداً متوقف نمی‌شود. ممکن است migration قبل از شکست تغییر کرده باشد؛ وضعیت ثبت‌شده را بررسی کنید.
- شکست app بعد از تعویض: اگر **هم رکوردهای migration و هم اثرانگشت schema** نسبت به قبل ثابت باشند، ابزار ایمیج قبلی را بالا می‌آورد و سلامت آن را دوباره بررسی می‌کند.
- تغییر schema، شکست migration، یا نامعلوم‌بودن سازگاری: بازگشت خودکار انجام نمی‌شود؛ وضعیت `needs_attention` و اطلاعات بازگشت محفوظ می‌مانند. این ابزار **هیچ‌وقت دیتابیس را خودکار restore نمی‌کند**.
- سالم‌بودن origin و شکست صرفاً تست عمومی HTTPS: نسخهٔ سالم جدید بی‌دلیل rollback نمی‌شود؛ وضعیت `needs_attention` ثبت می‌شود تا مسیر Cloudflare/شبکه بررسی شود.
- در rollback ممکن است Git برای حفظ تاریخچه روی commit قبلی به حالت detached برود؛ اجرای بعدی ابزار همچنان برنچ مشخص‌شده را دریافت می‌کند.

اگر `failed`، `rolled_back` یا `needs_attention` دیدید، پشت سرهم اجرا نکنید. ابتدا `iec-deploy status` و `iec-deploy logs` را بخوانید. برای بازگشت همراه با تغییر schema باید سازگاری نسخهٔ قبلی جداگانه بررسی شود؛ restore بک‌آپ می‌تواند اطلاعات جدید کاربران را از بین ببرد و نیاز به تصمیم صریح مالک دارد.

## لاگ و فایل‌های خصوصی

هر اجرا در `/var/backups/iec-expotrack/deployments/JOB_ID` ذخیره می‌شود: لاگ، state، بک‌آپ، hash، SHA و ایمیج بازگشت. پوشه‌ها root-only با دسترسی 700 و فایل‌ها 600 هستند. مقادیر حساس شناخته‌شده در خروجی فرمان‌ها پوشانده می‌شوند؛ `.env` چاپ یا روی GitHub ارسال نمی‌شود. بااین‌حال لاگ‌ها و بک‌آپ‌ها را عمومی نکنید.

بک‌آپ‌ها و ایمیج‌ها خودکار حذف نمی‌شوند. ابزار اگر فضای کافی نباشد متوقف می‌شود. نگهداری حداقل هفت بک‌آپ روزانه و پاکسازی کنترل‌شدهٔ نسخه‌های قدیمی را جداگانه مدیریت کنید؛ اسکریپت بک‌آپ روزانهٔ قبلی به کار خود ادامه می‌دهد.

ابزار DNS، TLS، Nginx، فایروال، SSH، Cloudflare یا تنظیمات امنیتی ویندوز را تغییر نمی‌دهد. گرفتن پاسخ سالم از سرور جای بررسی واقعی ورود، دکمه‌ها و نمای تبلت در مرورگر کاربران را نمی‌گیرد؛ مشکل قبلی `Connection reset` ممکن است مستقل از deployment باقی بماند.

بعد از نصب، برای انتشارهای روزمره فقط از همین ابزار استفاده کنید. ایمیج‌ها با تگ اختصاصی هر اجرا نگه داشته می‌شوند؛ اجرای دستورهای دستی قدیمی Compose بدون override ثبت‌شده ممکن است به ایمیج دیگری اشاره کند.
